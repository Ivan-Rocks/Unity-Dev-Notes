# 问题跟踪与后续开发事项

评估日期：2026-11-05  
最近更新：2026-11-05  
范围：本地仓库的脚本、契约、使用文档和现有笔记；未验证远程权限、真实多人协作或实际节省的排障时间。

## 目标与当前判断

本系统的目标是让实验室里一个人解决过的问题，能够被其他学生找到、判断是否适用，并独立复用。效果应按「记录 → 查找 → 判断适用性 → 解决问题 → 反馈」评估，不能只看上传数量。

当前已有 Markdown 模板、元数据契约、agent 投稿技能、Git 发布脚本和索引，适合开展小范围试点。主要缺口是检索入口、技术验证记录、复用反馈，以及发布和审核环节的一致性。

优先沉淀真实发生的 Unity / AR / 设备兼容性问题，特别是曾耗费排障时间、其他成员可能再次遇到的问题。通用知识可以作为补充。现有 IPv6 连接问题笔记包含具体环境、诊断步骤、修复验证和适用限制，可作为案例参考，但不代表已经完成独立复现。

## 跟踪规则

- 状态：待处理 / 进行中 / 待验证 / 已完成 / 暂缓。
- 优先级：P0 = 多人试点前需要解决或核实；P1 = 完成主要使用闭环；P2 = 根据试点结果逐步完善。
- 类型：已确认问题 / 待核实风险 / 功能缺口 / 流程改进。建议不等于已实现功能。
- 开始处理时登记负责人；完成时补充日期、提交或 PR 链接和验收证据，再更新状态。
- 保留问题编号，不因完成而删除；范围变化时更新条目并记录原因。

## 问题与验收标准

### UDN-001：使用标准 YAML 解析并修复索引字段

证据：[vault.ps1](../tools/vault.ps1) 的 `Read-Frontmatter` 使用逐行正则，并将嵌套字段写入同一个字典；`source` 内的 `title` 可能覆盖顶层标题。现有 [index.json](../notes/index.json) 中 IPv6 笔记的 `updated` 已包含额外的单引号。标题覆盖属于代码路径判断，尚未单独运行复现。

影响：学生可能搜不到正确标题；管理员与后续 agent 获得错误的元数据。

- [ ] 使用标准 YAML 解析，正确处理嵌套对象、数组、引号和日期。
- [ ] 统一日期输出规则，重建现有索引。
- [ ] 验收：带多个 source、带引号日期和多行数组的笔记均正确解析；索引标题保持顶层标题，日期为约定格式。

### UDN-002：实际执行 schema 校验并正确报告失败

证据：`Validate-Frontmatter` 只检查部分必填项、ID 和枚举，没有读取 [note.schema.json](contracts/note.schema.json)；`Test-Note` 失败时只打印 FAIL，不以失败退出码结束。文档声称使用 schema 校验，与实现不一致。

- [ ] 解析后按 schema 校验，明确启用日期等 format 检查。
- [ ] 增加文件名与 ID 一致、目录与 category 一致、ID 唯一、必要正文标题等检查。
- [ ] 校验失败返回非零退出码，并阻止发布；将检查接入 PR 自动校验。
- [ ] 验收：非法日期、错误类型、缺字段、错误目录和重复 ID 均被识别；合法笔记通过；自动流程能正确判断失败。

### UDN-003：保证审核后和多人合并后的索引一致

证据：`post` 在草稿阶段生成索引；[管理员手册](admin.md) 要求随后将正文状态改为 formalized，却称索引无需手动修改。状态修改后没有自动重建保证。多人同时改同一份生成索引也会带来冲突风险。

影响：已审核笔记可能仍被索引标成 draft，导致按 formalized 过滤时漏检。

- [ ] 确定索引生成时机，保证最终合并内容与索引一致。
- [ ] 自动检测索引漂移；冲突时从最终笔记集合重建，不手工拼接。
- [ ] 同步修正管理员手册。
- [ ] 验收：草稿改状态后索引同步；两人分别新增笔记并合并后，两篇均可检索，状态与正文一致。

### UDN-004：完成 PR 创建并准确展示发布状态

证据：`Publish-Note` 仅 push 分支并打印 GitHub compare URL；没有创建 PR。[上手文档](onboarding.md) 和管理员手册容易让人以为提交后已有待审 PR。

- [ ] 自动创建 PR，或明确提示用户还必须完成创建步骤；推荐实现自动创建。
- [ ] 明确区分「本地草稿、分支已上传、PR 待审核、正式入库」。
- [ ] 自动创建时处理认证失败和已有 PR，避免重复创建。
- [ ] 验收：成功返回真实 PR 地址，管理员能看到待审项；失败时不会显示已入库。

### UDN-005：发布失败恢复与本地工作区保护

证据：发布依次切分支、复制、提交、push；没有明确恢复机制。push 失败后再次 post 可能遇到已有分支。脚本也未在开始时明确检查并隔离已有暂存内容。

- [ ] 发布前检查工作区、暂存区和当前分支，保护用户已有修改。
- [ ] 支持从已有分支或提交继续上传，并给出具体下一步。
- [ ] 核查 sync 冲突后的退出状态和说明，避免错误被当作同步成功。
- [ ] 验收：模拟 push 失败后可恢复；重复执行不生成重复内容；已有无关暂存修改不会混入笔记提交。

### UDN-006：核实并落实主分支审核保护

证据：管理员手册给成员 Write 权限；本地脚本接受 formalized 状态。远程分支保护和权限尚未检查，不能据此断言远程可绕过审核。

- [ ] 核实实际仓库的主分支保护、PR 审核和必要自动检查。
- [ ] 明确学生、管理员和 agent 的权限与例外规则。
- [ ] 投稿流程默认 draft；正式状态转换与审核要求一致。
- [ ] 验收：记录实际配置；普通贡献者无法按正常权限绕过既定审核规则直接发布正式内容。

### UDN-007：提供面向报错与症状的检索入口

证据：[agent-integration.md](agent-integration.md) 将检索列为未来功能。目前有索引，但没有已实现的专用查询入口。

- [ ] 支持粘贴错误信息或自然语言症状，按标题、摘要、标签、错误码及别名查询。
- [ ] 返回少量相关结果及原文链接，展示适用环境与验证情况。
- [ ] 草稿、已废弃内容应明确标记；没有可靠命中时明确说明。
- [ ] 优先实现轻量检索，根据实际漏检再决定是否引入向量检索。
- [ ] 验收：使用试点真实报错和不同说法验证检索；记录漏检、误匹配，用户能直接打开对应答案。

### UDN-008：区分编辑状态、验证情况和适用环境

问题：formalized 只能说明编辑流程状态，不能证明他人复现成功。Unity 版本是可选字段，管线、插件、系统和设备信息尚未结构化。

- [ ] 分别记录编辑状态和验证情况，例如作者验证、他人复现、部分环境有效、未验证。
- [ ] 按问题需要记录 Unity、渲染管线、插件、系统和设备版本，不强迫所有笔记填写无关字段。
- [ ] 记录验证者、验证时间和结果；允许原因待确认、临时绕过等明确表述。
- [ ] 由 agent 提取已有信息，只追问影响适用性判断的缺项。
- [ ] 验收：读者能区分「整理过」与「验证过」，能判断自己的环境是否匹配；旧笔记有明确迁移规则。

### UDN-009：支持旧笔记修订、重复提示和复用反馈

证据：当前 post 对已有 ID 直接拒绝，适合新增但未提供修订入口。

- [ ] 支持基于已有 ID 创建修订 PR，保留历史和引用。
- [ ] 新增前提示相似笔记，允许选择补充旧笔记。
- [ ] 提供「解决了 / 未解决 / 仅某环境有效」反馈，并通知维护者。
- [ ] 验收：学生能完成一次补充或纠错；重复问题可归并；失败反馈能被追踪处理。

### UDN-010：降低首次安装与技能更新成本

问题：首次使用涉及 Git、账号、权限、认证、DSH 和技能复制；文档的「约 5 分钟」尚未经过新用户实测。技能更新依赖逐人重新复制。

- [ ] 提供初始化检查和清晰的失败指引，覆盖账号权限、认证、路径和技能可用性。
- [ ] 建立技能版本检查与更新机制。
- [ ] 保留简单的备用投稿方式，避免环境未装好就无法贡献。
- [ ] 验收：未参与开发的学生独立完成首次投稿；记录实际耗时、失败环节及是否需要管理员介入。

### UDN-011：调整正文结构，保留人类排障所需信息

证据：[note-spec.md](note-spec.md) 要求将细节和排障分支全部下沉到 AI Prompt。学生手动排障也需要这些内容，过度追求一屏可能损害可执行性。

- [ ] 正文保留适用条件、诊断步骤、解决方法、验证方式及重要限制。
- [ ] AI Prompt 只承载 agent 使用指引，不作为关键事实的唯一位置。
- [ ] 对无外部参考的原创排障记录允许提供日志、复现或验证证据，避免为满足来源格式编造链接。
- [ ] 验收：学生不依赖 AI Prompt 也能完成诊断和结果验证；模板、规范和审核清单一致。

### UDN-012：分担审核职责并建立维护机制

问题：当前管理员需要同时检查格式、重复、来源、技术正确性和状态，容易成为瓶颈。

- [ ] 自动检查格式；作者提供环境与验证；相关方向成员复核技术；管理员维护权限和审核分配。
- [ ] 设置维护责任人与最近验证时间，提供过期、失效及重复内容的处理方式。
- [ ] 根据试点确定审核规则和处理周期，不要求所有笔记采用相同审核负担。
- [ ] 验收：待审项有负责人；管理员缺席时仍有交接路径；失效笔记有状态和替代链接。

### UDN-013：开展效果试点并记录收益与成本

建议邀请 3–5 位学生开展两周试点。以下为待执行方案，不代表已有使用数据。

- [ ] 收集真实排障案例，记录是否存在相关笔记、是否找到、是否适用及是否解决。
- [ ] 记录检索到解决的耗时、是否向原作者求助、投稿耗时、审核耗时和发布失败情况。
- [ ] 记录无命中和复用失败的原因，以决定下一轮开发优先级。
- [ ] 对未使用知识库的可比案例记录基线；没有可比数据时，不宣称节省了确定比例的时间。
- [ ] 验收：形成试点复盘，包含成功与失败案例、贡献与维护成本、下一轮优先级；重点核实是否有人能凭他人的笔记独立解决问题。

## 建议开发顺序与依赖

1. 修复解析与校验（001、002），再建立索引一致性（003）。
2. 完成发布、恢复和权限核实（004–006），对齐使用文档后开展多人试用。
3. 优先补查询入口（007），同时完善适用环境与正文结构（008、011）。
4. 补充修订反馈和安装体验（009、010），开展并持续记录试点（013）。
5. 根据试点结果调整维护分工（012）及后续 RAG、自动化维护投入。

与 BNU-agent 的衔接放在知识能够可靠查询和验证之后：让 Unity 开发阶段检索相关经验、依据适用环境使用，并将实际验证结果反馈到笔记库。
